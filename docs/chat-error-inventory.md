# Web chat inline error inventory

This inventory covers failed-message feedback rendered below messages in the AI conversation body. Toasts, share landing pages, resource pickers, delete confirmations, save/share dialogs, standalone execution cards and raw command stdout/stderr are outside this change.

## Scope and evidence

- The display boundary is `src/page/chat/messages/index.tsx`: failed messages render `ChatErrorText` using the current interface language.
- The classifier has 30 display categories, 50 explicit business/transport codes, 63 exact English legacy aliases, HTTP status fallbacks and an unknown-error fallback.
- The original requester screenshot shows `Software caused connection abort` in the mobile app. It establishes the reported symptom, not a naturally reproduced Web failure or a mobile implementation change.
- Local browser verification on 2026-11-02 checked all 30 categories in Chinese and English using controlled history responses. It also checked live language switching, a controlled connection interruption during a real send, successful retry against the test backend and persistence after refresh. These are controlled display/transport checks, not 30 naturally reproduced service faults.
- Arbitrary provider text, HTML, arrays, objects and private diagnostic details are never rendered as the product error message. Unrecognized details use a safe localized fallback.

## Implementation boundaries

1. `Messages` owns one localized failure row and one applicable retry button. `UserMessage` and `DecisionReceipt` do not duplicate failed-send feedback.
2. `ChatErrorText` resolves the category at render time. A visible historical error changes when the interface language changes.
3. `streamTransport.ts` preserves available HTTP metadata and classifies fetch/read failures. Explicit cancellation remains a control-flow event.
4. `messageProcessor.ts` accepts JSON or plain-text error events and retains scalar diagnostic metadata for classification.
5. `messageOperator.ts` stores message/code/status on failed messages and removes stale error metadata after recovery, completion or stop.
6. `conversationHistory.ts` preserves local metadata only while merging the same failure. Cold history depends on the fields actually returned by the server; no backend persistence/schema changes are included.
7. Conversation image upload retains available error metadata and lets the inline row own send-time errors. Other upload callers keep their existing behavior.
8. Normal AI/user content and raw tool output are not classified or rewritten. Errors are not automatically retried.

## Reachable message flow

A send starts with a local pending message. Image upload rejection, a stream error event or a transport failure can mark the message as failed. The message list then renders the localized inline error. Explicit recognized codes take precedence, followed by a timeout exception, exact legacy aliases, HTTP status fallbacks and a safe unknown fallback. Generic legacy aliases allow more specific HTTP status information to take precedence.

## HTTP and fallback behavior

| Input                                  | Display category                  | Notes                                                        |
| -------------------------------------- | --------------------------------- | ------------------------------------------------------------ |
| HTTP 401                               | `chat.errors.unauthorized`        | Existing authentication handling is preserved                |
| HTTP 403                               | `chat.errors.forbidden`           | An explicit business code can select a more precise category |
| HTTP 404                               | `chat.errors.not_found`           | An explicit business code can select a more precise category |
| HTTP 408 / 504                         | `chat.errors.timeout`             | Ask the user to inspect the result                           |
| HTTP 413                               | `chat.errors.file_too_large`      | File size rejection                                          |
| HTTP 415                               | `chat.errors.unsupported_file`    | File type rejection                                          |
| HTTP 429                               | `chat.errors.rate_limited`        | Rate limiting                                                |
| Other HTTP 5xx / HTML gateway response | `chat.errors.service_unavailable` | Raw HTML is not shown                                        |
| Other HTTP 4xx / validation array      | `chat.errors.invalid_request`     | Dynamic field details are not shown                          |
| Unknown details without code/status    | `chat.errors.unknown`             | No diagnostic text disclosure                                |
| AbortError / Axios cancellation        | No inline failure                 | Handled by `isChatCancellation()`                            |

## Dynamic messages without an exact alias

These source patterns do not have an exact legacy-message mapping. Available code/status is used; otherwise the safe fallback applies. They must not be presented as verified precise classifications.

| Source message / pattern                                          | Source                                         | Result                                                                                          |
| ----------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `Response failed`                                                 | Backend stream recovery without error metadata | Unknown without code/status                                                                     |
| `Invalid response_type = {responseType}`                          | Backend/Wizard protocol                        | Unknown without code/status                                                                     |
| `Unknown response type: {type}`                                   | Backend Wizard stream                          | Unknown without code/status                                                                     |
| `Environment variable {variable} is required`                     | Backend configuration                          | Only the exact OBB_WIZARD_BASE_URL alias maps to service unavailable; others use status/unknown |
| `Request failed with status {status}`                             | Backend request fallback                       | HTTP category when status is retained, otherwise unknown                                        |
| `Your file ({userSize}) exceeds the maximum limit of {limitSize}` | Backend file validation                        | File too large with a recognized code or HTTP 413, otherwise status/unknown                     |
| Arbitrary provider text, HTML, objects, arrays or private details | Upstream/middleware                            | Safe fallback; original details are not displayed                                               |

## Verification limits

The code and unit checks establish the finite display categories for known inputs at the inline boundary. Controlled local browser checks establish bilingual rendering and the exercised send/retry behavior. Real provider faults, quota/storage exhaustion, device permission changes, expired approvals, independent shared-chat permission flows and requester acceptance remain unverified. No Android/iOS implementation, external-page error localization, backend deployment or database changes are part of this narrowed change.
